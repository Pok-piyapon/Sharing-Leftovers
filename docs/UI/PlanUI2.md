# แผนสร้างหน้า UI — Sharing Leftovers

แบ่งเป็น Phase พร้อม Checklist ตรวจงานในแต่ละช่วง | อ้างอิง User Flow, Admin Flow และแผน EJS ของโปรเจกต์ | โฟกัสเฉพาะฝั่ง UI

## วิธีใช้เอกสารนี้

- ทำตามลำดับ Phase เพราะหน้าที่อยู่ท้าย ๆ ใช้ Component และ Flow จากหน้าก่อนหน้า
- ก่อนปิดแต่ละ Phase ให้ติ๊ก Checklist ของ Phase นั้น และ Checklist กลางด้านล่างให้ครบ
- Phase ถือว่าเสร็จเมื่อผ่านข้อ Definition of Done ของ Phase นั้น
- Checklist นี้เป็นเครื่องมือวางแผน ไม่ใช่สถานะความสำเร็จของโค้ดปัจจุบัน

## ข้อตกลงที่ตกลงแล้ว

- ประกาศถูกยกเลิก (โดยเจ้าของหรือ Admin): คำขอ pending เปลี่ยนเป็น `cancelled` ทั้งหมด (ไม่ใช้ `rejected`), คำขอ approved ที่ยังไม่ส่งมอบเป็น `cancelled` พร้อมคืนสต็อก, คำขอ completed คงเดิม
- Admin ระงับและปลดระงับบัญชีได้ (`isActive`) แต่ตั้งใครเป็น Admin ไม่ได้: UI ไม่มีตัวเลือกเปลี่ยน role และฝั่งเซิร์ฟเวอร์ไม่ประมวลผลฟิลด์ `role`
- ผลต่อ UI: ผู้ขอเห็น Badge ยกเลิกแล้ว พร้อมข้อความแยกสาเหตุ (ผู้ขอยกเลิกเอง หรือประกาศนี้ถูกยกเลิก) และ Dialog ยกเลิกประกาศบอกผลตรงตามนี้

## หลักการทำ UI ให้ต่อ API ทีหลังได้ง่าย

1. Template และ Web Controller เรียกข้อมูลผ่าน Service Layer เท่านั้น ไม่ query หรือยิง API ตรงจากหน้า วันที่ API พร้อมให้เปลี่ยนเฉพาะไส้ในของ Service
2. กำหนดรูปข้อมูลที่แต่ละหน้าต้องใช้ (เช่น การ์ดประกาศต้องมี `pendingCount` ไหม) ก่อนสร้างหน้า แล้วให้ Backend ปรับตามทีหลัง
3. Component รับฟิลด์ที่อาจยังไม่มีได้ ถ้าไม่มีข้อมูลให้ซ่อนส่วนนั้นหรือแสดงค่าสำรอง ห้ามแสดงเลข 0 หรือข้อความสมมติที่ผิดความจริง
4. ใช้ข้อมูลจำลอง (Mock/Seed) ระหว่างพัฒนา ให้เห็นทุกสถานะของหน้าได้ครบ
5. ปุ่มที่ยังไม่มี endpoint รองรับต้องปิดด้วย flag หรือแสดงเป็นปุ่มที่กดไม่ได้ ห้ามปล่อยขึ้น Production ในสภาพยิงไปไม่ถึง
6. กฎธุรกิจและสิทธิ์อยู่ฝั่งเซิร์ฟเวอร์เสมอ UI ซ่อนปุ่มได้ แต่ไม่ใช่การตรวจสิทธิ์

## จุดที่อาจต้องมี API เพิ่ม

เช็กกับโค้ดจริงอีกครั้งก่อนเริ่มแต่ละ Phase ที่เกี่ยวข้อง

| ส่วนใน UI | สิ่งที่ API อาจยังไม่มี | ทำ UI ไว้ก่อนอย่างไร | Phase |
| --- | --- | --- | --- |
| การ์ดสถิติที่ `/admin` | Endpoint สรุปตัวเลข | แสดงเฉพาะการ์ดที่มีข้อมูล ซ่อนการ์ดที่ยังไม่มี | 8 |
| เหตุผลการระงับบัญชี | ที่เก็บเหตุผล (`PATCH /users/:id/status` รับแค่ `isActive`) | ทำช่องเหตุผลไว้ในฟอร์ม ส่งไปกับคำสั่งเมื่อ API รองรับ | 9 |
| Badge แจ้งเตือนและการเคลียร์เมื่อเปิดหน้า | Endpoint นับและ mark as read รวมถึงชื่อฟิลด์ที่ขัดกัน (`isRead` กับ `isReadByRequester`) | ตกลงชื่อฟิลด์เดียวก่อน แล้วให้ Service คืนค่าว่างเพื่อซ่อน Badge จนกว่า API จะพร้อม | 3, 5 |
| จำนวนคำขอรอพิจารณาในประกาศของฉัน | `GET /users/me/listings` อาจยังไม่คืน `pendingCount` | ซ่อนชิปจำนวนคำขอที่รอ | 6 |
| จำนวนประกาศที่ใช้ในแต่ละหมวดหมู่ | `usageCount` | ซ่อนคอลัมน์ และใช้ข้อความเตือนกลางตอนลบ | 9 |
| ปุ่มขอรับของถูกปิดเมื่อเคยขอแล้ว | วิธีบอกว่าผู้ใช้เคยขอประกาศนี้หรือยัง | ปล่อยปุ่มกดได้ แล้วจัดการ Error ซ้ำจากเซิร์ฟเวอร์ | 2, 3 |
| อัปโหลดรูปจริง | Upload Service | ทำช่องรูปเป็น Component เดียวที่ส่งออกเป็น array ของ URL สลับเป็นอัปโหลดทีหลังได้ | 6 |

## Checklist กลาง (ใช้ตรวจทุกหน้าก่อนปิด Phase)

- [ ] ครบ 4 สถานะของข้อมูล: กำลังโหลด / ปกติ / ไม่มีข้อมูล (Empty State) / เกิดข้อผิดพลาด
- [ ] Responsive ที่ 375px, 768px, 1280px และ body ไม่เลื่อนแนวนอน (ตารางเลื่อนในกรอบของตัวเอง)
- [ ] Contrast ตัวอักษรอย่างน้อย 4.5:1 โดยเฉพาะตัวขาวบนเขียว `#246B4A` และตัวเล็กบน Terracotta `#B85C38`
- [ ] ปุ่มและลิงก์กดง่าย (สูงอย่างน้อย 44px) มี label ครบ Tab ได้ เห็น Focus ชัด รูปมี alt
- [ ] ข้อความที่ผู้ใช้กรอกแสดงด้วย `<%= %>` (Escape) และใช้ `<%- %>` เฉพาะ include
- [ ] ฟอร์มที่เปลี่ยนข้อมูลมี CSRF Token กันกดซ้ำระหว่างส่ง และเก็บค่าที่กรอกไว้เมื่อ Validation ไม่ผ่าน
- [ ] ปุ่มที่ซ่อนตามบทบาทมีการตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ด้วย (ทดสอบพิมพ์ URL ตรง)
- [ ] สถานะและข้อผิดพลาดแสดงเป็นข้อความที่คนอ่านเข้าใจ ไม่แสดงค่า enum ดิบ
- [ ] มี Toast/Flash แจ้งผลสำเร็จและผิดพลาด
- [ ] สี ฟอนต์ ระยะห่าง ตรงกับ Design Tokens และสอดคล้องกับ Mockup

## Phase 0 — โครงพื้นฐานและ Components กลาง

**เป้าหมาย:** มี Layout และชิ้นส่วน UI ที่ทุกหน้าใช้ร่วมกัน เพื่อไม่ต้องเขียนซ้ำ

**ผลลัพธ์:** `tokens.css`, `layout.css`, `components.css`, partials ใน `views/partials/`, หน้า Error

**Setup**

- [x] ตั้ง View Engine เป็น EJS และชี้โฟลเดอร์ views/public ถูกต้อง
- [x] Web Route `GET /` ไม่ซ้ำกับ Route เดิม และ API เดิม (`/api/v1/*`, `/api-docs`) ยังทำงาน
- [x] Middleware `attachLocals` ส่ง `currentUser` (ไม่มี passwordHash), `isAuthenticated`, `flash`, `csrfToken`, จำนวนคำขอที่ยังไม่อ่าน

**Design Tokens**

- [x] กำหนดสี: Forest Green `#246B4A`, Warm Neutral `#F7F7F2`, White `#FFFFFF`, Terracotta `#B85C38`
- [x] กำหนดฟอนต์ไทย (Noto Sans Thai) ขนาดตัวอักษร Radius เงา ระยะห่าง
- [x] กำหนดสี Badge สถานะประกาศ (พร้อมรับ, จองเต็มแล้ว, ส่งมอบครบ, ยกเลิก, หมดอายุ) และสถานะคำขอ (รอ, อนุมัติ, ไม่อนุมัติ, ยกเลิก, ส่งมอบแล้ว)

**Partials และ Components**

- [x] `head`, `header`, `footer`, `flash`, `pagination`, `empty-state`
- [x] `listing-card` รับข้อมูล 1 ประกาศ ใช้ซ้ำได้ทั้งหน้าแรก /listings และ Dashboard
- [x] Header แยก 3 แบบ: Guest / Member / Admin (Admin ซ่อน เริ่มแบ่งปัน และ พื้นที่ของฉัน)
- [x] ปุ่ม Primary / Outline / Danger, Input, Select, Textarea พร้อมข้อความ Error ใต้ช่อง
- [x] Badge สถานะ, Modal (Focus Trap, ปิดด้วย Esc), Confirm Dialog, Toast, Skeleton
- [x] หน้า 404, 403, 500 มีปุ่มกลับหน้าหลัก

**ข้อมูลและ Service (เพื่อให้ต่อ API ทีหลังได้ง่าย)**

- [x] Web Controller เรียกข้อมูลผ่าน Service เท่านั้น (`listing.service`, `reservation.service` ฯลฯ) ไม่มี query หรือ fetch ตรงใน Template
- [x] เขียนสรุปรูปข้อมูลที่แต่ละหน้าต้องใช้ (View Model) ก่อนสร้างหน้า และระบุฟิลด์ที่ API อาจยังไม่มี
- [x] ตกลงชื่อฟิลด์ที่ขัดกันให้เหลือชื่อเดียว (เช่น `isRead` กับ `isReadByRequester`)
- [x] ชุดข้อมูลจำลอง (Mock/Seed) ครอบคลุมทุกสถานะ: ประกาศ 5 สถานะ, คำขอ 5 สถานะ, รายงาน 4 สถานะ, ผู้ใช้ที่ถูกระงับ, ประกาศที่ไม่มีรูป และชื่อ/ข้อความยาวผิดปกติ
- [x] Component ทุกตัวรับฟิลด์ที่อาจยังไม่มีได้ ถ้าไม่มีให้ซ่อนส่วนนั้น ไม่แสดงเลข 0 หรือข้อความสมมติ

- [x] ข้อมูลจำลองใช้เฉพาะตอนพัฒนา ไม่หลุดไป Production

**Definition of Done:** สร้างหน้าเปล่าที่ใช้ Layout กลางได้ Header แสดงถูกต้องตามบทบาท และเรียกใช้ Component ทุกตัวได้ (ผ่านแล้ว ✅)

## Phase 1 — ค้นหาสิ่งของ `/listings`

**เป้าหมาย:** ผู้เข้าชมค้นหาและกรองสิ่งของได้โดยไม่ต้องเข้าสู่ระบบ

**ข้อมูลที่แสดง:** Listing Card, จำนวนที่พบ, ตัวกรองที่เลือกอยู่

- [ ] ช่องค้นหาข้อความ
- [ ] ตัวกรองหมวดหมู่ (เฉพาะที่เปิดใช้งาน) และสภาพ (ใหม่, เหมือนใหม่, ดี, พอใช้, มีตำหนิ)
- [ ] โหมดพื้นที่ 2 แบบ: ใกล้ฉัน (GPS + รัศมี) และเลือกเอง (จังหวัด → อำเภอ → ตำบล แบบต่อเนื่อง)
- [ ] เมื่อผู้ใช้ปฏิเสธ GPS แสดงข้อความสุภาพและสลับไปโหมดเลือกพื้นที่เอง
- [ ] เรียงลำดับ: ใหม่ล่าสุด, ใกล้หมดเวลา, ยอดนิยม
- [ ] Query String เก็บค่าตัวกรองทั้งหมด แชร์ลิงก์ได้ กด Back/Refresh แล้วผลเหมือนเดิม
- [ ] ชิปตัวกรองที่เลือกอยู่ กดลบทีละตัวได้ และมีปุ่มล้างทั้งหมด
- [ ] Pagination ทำงานและคงตัวกรองไว้
- [ ] การ์ดแสดงครบ: รูป, Badge สถานะ, ชื่อ, หมวดหมู่, สภาพ, เหลือกี่จากกี่ชิ้น, พื้นที่หรือระยะทางโดยประมาณ, เวลาที่เหลือ
- [ ] ประกาศที่จองเต็มแล้วแสดงแบบจาง แต่ยังกดดูได้
- [ ] ไม่มีที่อยู่ละเอียด พิกัดแม่นยำ หรือเบอร์โทรอยู่ใน HTML ของหน้านี้
- [ ] Empty State พร้อมปุ่มล้างตัวกรอง
- [ ] มือถือ: ตัวกรองเป็น Drawer และมีปุ่มเปิดที่เห็นชัด
- [ ] Admin เปิดหน้านี้เพื่อตรวจตราได้ตามปกติ

**Definition of Done:** ค้นหา กรอง เรียง เปลี่ยนหน้า แล้วกด Back กลับมาได้ผลเดิม และใช้งานครบทั้งมีและไม่มี GPS

## Phase 2 — รายละเอียดสิ่งของ `/listings/:id`

**เป้าหมาย:** ช่วยให้ตัดสินใจขอรับของ โดยยึด Privacy by Design

**ข้อมูลที่แสดง:** รูป 1-5 รูป, ชื่อ, หมวดหมู่, สภาพ, คงเหลือ/ทั้งหมด, รายละเอียด, พื้นที่คร่าว ๆ, ช่วงเวลานัดรับ, วันหมดอายุ, ชื่อเจ้าของ

- [ ] แกลเลอรีรูป (รูปหลัก + Thumbnail) และมีรูปสำรองเมื่อโหลดรูปไม่สำเร็จ
- [ ] Breadcrumb และปุ่มกลับไปผลการค้นหาเดิม
- [ ] กล่องข้อมูลนัดรับแบบล็อก 🔒 พร้อมข้อความว่าจะเปิดเมื่อเจ้าของอนุมัติ
- [ ] กล่องข้อมูลนัดรับแบบเปิด (เมื่อคำขอเป็น approved): ที่อยู่ละเอียด, เบอร์โทร, ช่วงเวลา, ปุ่มคัดลอก
- [ ] ตรวจ View Source ในฐานะ Guest และสมาชิกทั่วไป ต้องไม่เห็นที่อยู่ละเอียด พิกัดแม่นยำ หรือเบอร์โทร
- [ ] ปุ่มหลักเปลี่ยนตามผู้ดู ครบทุกกรณี:
  - [ ] Guest: ขอรับของชิ้นนี้ (พาไป /auth พร้อม returnTo)
  - [ ] สมาชิกทั่วไป: ขอรับของชิ้นนี้ (เปิด Modal)
  - [ ] เคยขอแล้ว: ปุ่มปิด + ข้อความ คุณเคยส่งคำขอสำหรับสิ่งของชิ้นนี้ไปแล้ว + ลิงก์ไป /reservations/my
  - [ ] เจ้าของประกาศ: จัดการคำขอ / แก้ไข (เมื่อยังไม่มีคำขอ) / ยกเลิกประกาศ
  - [ ] Admin: ซ่อนปุ่มขอรับ และมีปุ่ม ยกเลิกประกาศนี้ (Admin)
  - [ ] ประกาศ reserved / completed / cancelled / expired: ปุ่มปิด + แถบอธิบายเหตุผล
- [ ] มือถือ: ปุ่มหลักติดขอบล่าง (Sticky)
- [ ] ปุ่ม 🚩 รายงานปัญหา แสดงเฉพาะสมาชิกทั่วไป

* [ ] ถ้า API ยังไม่บอกว่าผู้ใช้เคยขอประกาศนี้หรือยัง ให้ปุ่มขอรับกดได้ แล้วจัดการ Error ซ้ำจากเซิร์ฟเวอร์ด้วยข้อความ คุณเคยส่งคำขอสำหรับสิ่งของชิ้นนี้ไปแล้ว และสลับปุ่มเป็นปิดทันทีหลังได้รับ Error นั้น

**Definition of Done:** ทุกกรณีของผู้ดูแสดงปุ่มและข้อความถูกต้อง และข้อมูลส่วนตัวไม่รั่วไหลใน HTML

## Phase 3 — เข้าสู่ระบบ, Header ตามบทบาท, Modal ขอรับของ/รายงาน

**เป้าหมาย:** ผู้ใช้เข้าสู่ระบบแล้วกลับมาทำรายการต่อได้อย่างต่อเนื่อง

**หน้า `/auth`**

- [ ] แท็บ เข้าสู่ระบบ | สมัครสมาชิก ในหน้าเดียว
- [ ] ฟิลด์สมัคร: ชื่อ, อีเมล, เบอร์โทร, รหัสผ่าน (ขั้นต่ำ 8 ตัว) พร้อมปุ่มแสดง/ซ่อนรหัสผ่าน
- [ ] สมัครสำเร็จแล้ว Auto-login
- [ ] Error ใต้ช่อง: อีเมลซ้ำ, รหัสผ่านไม่ถูกต้อง, ข้อมูลไม่ครบ และเก็บค่าที่กรอกไว้
- [ ] บัญชีที่ถูกระงับแสดงข้อความ บัญชีของคุณถูกระงับการใช้งาน
- [ ] มีแถบแจ้งเมื่อมี returnTo เช่น เข้าสู่ระบบเพื่อขอรับของชิ้นนี้ต่อ
- [ ] returnTo รับเฉพาะ Path ภายในที่ขึ้นต้นด้วย `/` (ทดสอบแล้วว่า `//evil.com` และ `https://...` ถูกปฏิเสธ)
- [ ] หลังเข้าสู่ระบบกลับมาที่ `/listings/:id?action=claim` แล้ว Modal ขอรับของเปิดเอง
- [ ] ออกจากระบบแล้ว Header กลับเป็นแบบ Guest

**Modal ขอรับของ**

- [ ] เลือกจำนวนได้ตั้งแต่ 1 ถึงจำนวนคงเหลือ
- [ ] ช่องข้อความถึงเจ้าของ
- [ ] ข้อความเตือนว่าขอได้ครั้งเดียวต่อประกาศ
- [ ] ส่งสำเร็จ: Toast + ปุ่มบนหน้ากลายเป็นแบบปิดและมีลิงก์ไป /reservations/my
- [ ] จัดการ Error: สต็อกเปลี่ยน, เคยขอแล้ว, ขอของตัวเอง, ประกาศปิดไปแล้ว

**Modal รายงานปัญหา**

- [ ] เลือกเหตุผล 6 แบบ (สแปม, ไม่เหมาะสม, หลอกลวง, ผิดกฎหมาย, ข้อมูลเท็จ, อื่น ๆ) + ช่องรายละเอียด
- [ ] ส่งสำเร็จ: Toast ส่งรายงานเรียบร้อยแล้ว ทีมงานจะตรวจสอบโดยเร็ว
- [ ] รายงานซ้ำแสดงข้อความว่าเคยรายงานประกาศนี้แล้ว
- [ ] Guest กดรายงานแล้วชวนเข้าสู่ระบบก่อน

**Definition of Done:** Guest กดขอรับของ → สมัคร/เข้าสู่ระบบ → กลับมาเจอ Modal ขอรับของที่เปิดอยู่ และส่งคำขอสำเร็จ

## Phase 4 — หน้าแรก `/`

**เป้าหมาย:** พาผู้เข้าชมไปค้นหาหรือแบ่งปันได้เร็วที่สุด

- [ ] Hero: หัวข้อ, คำอธิบาย, ช่องค้นหาที่ส่งไป `/listings?search=...`
- [ ] ปุ่ม ค้นหาของใกล้ฉัน (ขอ GPS แล้วไปหน้า /listings)
- [ ] หมวดหมู่เป็นชิปไอคอน (เฉพาะที่เปิดใช้งาน) กดแล้วไป /listings พร้อมตัวกรอง
- [ ] ส่วน สิ่งของที่เพิ่งแบ่งปัน 6-8 ใบ ใช้ `listing-card` เดิม
- [ ] ขั้นตอนใช้งาน 3 ข้อ และลิงก์ไป /help/how-it-works
- [ ] ปุ่มชวนแบ่งปันเปลี่ยนตามบทบาท (Guest ไป /auth, Member ไป /listings/new, Admin ไม่แสดง)
- [ ] Empty State เมื่อยังไม่มีประกาศ

**Definition of Done:** จากหน้าแรกกดไปถึงผลการค้นหาที่ถูกต้องได้ทั้งจากช่องค้นหา หมวดหมู่ และปุ่มใกล้ฉัน

## Phase 5 — ฝั่งผู้ขอรับ `/dashboard` และ `/reservations/my`

**เป้าหมาย:** สมาชิกติดตามสถานะคำขอทั้งหมดได้จากที่เดียว

**หน้า `/dashboard`**

- [ ] แท็บ คำขอของฉัน | ประกาศของฉัน และจุดแจ้งเตือนบนแท็บ
- [ ] สรุปตัวเลข: ประกาศที่เปิดอยู่, คำขอรอพิจารณาที่ได้รับ, คำขอของฉันที่มีอัปเดต
- [ ] ปุ่มลัด เริ่มแบ่งปัน

**หน้า `/reservations/my`**

- [ ] การ์ดคำขอ: รูป, ชื่อสิ่งของ, จำนวนที่ขอ, วันที่ขอ, Badge สถานะ, ข้อความที่ส่งไป
- [ ] ตัวกรองสถานะ (ทั้งหมด, รอ, อนุมัติ, เสร็จสิ้น, อื่น ๆ)
- [ ] จุดแดง ใหม่ ในรายการที่ยังไม่อ่าน
- [ ] สถานะ approved: แสดงที่อยู่นัดรับเต็ม, เบอร์โทรเจ้าของ, ช่วงเวลา
- [ ] สถานะ rejected (เจ้าของปฏิเสธ) และ cancelled (ผู้ขอยกเลิกเอง หรือประกาศถูกยกเลิกจนคำขอ pending กลายเป็น cancelled): แสดงข้อความแยกสาเหตุ เช่น ประกาศนี้ถูกยกเลิก และซ่อนปุ่มยกเลิกคำขอเมื่อไม่มีอะไรให้ยกเลิกแล้ว
- [ ] ปุ่ม ยกเลิกคำขอ (เมื่อ pending หรือ approved) พร้อม Confirm Dialog
- [ ] เมื่อเปิดหน้านี้ Badge ที่ Navbar หายไป และตัวเลขตรงกับข้อมูลจริง (ถ้ายังไม่มี endpoint นับ/เคลียร์ ให้ซ่อน Badge ไว้ก่อน ไม่แสดงเลขสมมติ)
- [ ] Empty State พร้อมปุ่มไปค้นหาของ

**Definition of Done:** อนุมัติคำขอจากบัญชีเจ้าของ แล้วบัญชีผู้ขอเห็น Badge, สถานะใหม่ และข้อมูลนัดรับ จากนั้น Badge หายเมื่อเปิดหน้า

## Phase 6 — ฝั่งเจ้าของประกาศ

**เป้าหมาย:** ลงประกาศ จัดการคำขอ และส่งมอบได้ครบวงจร

**หน้า `/listings/new` และ `/listings/:id/edit`**

- [ ] ฟอร์มแบ่งเป็นการ์ดตอน: ข้อมูลสิ่งของ, รูปภาพ, การนัดรับ, วันหมดอายุ
- [ ] ฟิลด์บังคับ: ชื่อ, หมวดหมู่, สภาพ, จำนวน (ตั้งแต่ 1), รายละเอียด
- [ ] รูปภาพ: ใส่ URL ได้ 1-5 รูป, ตรวจรูปแบบ http/https, Preview ทันที, ลบ/จัดลำดับได้ และแยกเป็น Component ช่องรูปตัวเดียวที่ส่งออกเป็น array ของ URL เพื่อสลับเป็นอัปโหลดไฟล์ทีหลังโดยไม่ต้องแก้ส่วนอื่นของฟอร์ม
- [ ] การนัดรับ: แสดงชัดว่า นัดรับด้วยตนเองเท่านั้น (ไม่มีตัวเลือกจัดส่ง)
- [ ] แยกพื้นที่ที่เปิดสาธารณะ (จังหวัด/อำเภอ/ตำบล) ออกจากที่อยู่ละเอียดที่ถูกซ่อน และบอกผู้ใช้ให้ชัดเจน
- [ ] วันหมดอายุต้องเป็นเวลาในอนาคต
- [ ] หน้าแก้ไข: ถ้ามีคำขอแล้ว แสดงแถบล็อก ปิดทุกช่อง เหลือเฉพาะปุ่มยกเลิกประกาศ

**หน้า `/users/me/listings`**

- [ ] รายการ: รูป, ชื่อ, Badge สถานะ, คงเหลือ/ทั้งหมด, วันหมดอายุ, จำนวนคำขอ (เน้นคำขอที่รอพิจารณา ถ้า API ยังไม่คืนค่านี้ให้ซ่อนชิป ไม่แสดง 0)
- [ ] ตัวกรองสถานะ
- [ ] ปุ่มแก้ไขเป็นสีเทาพร้อม Tooltip เมื่อมีคำขอแล้ว
- [ ] ยกเลิกประกาศ: Confirm Dialog อธิบายว่าคำขอ pending และ approved ที่ยังไม่ส่งมอบจะเป็น cancelled ทั้งหมด และกู้คืนไม่ได้

**หน้า `/listings/:id/reservations`**

- [ ] ส่วนหัวสรุปประกาศ พร้อมตัวเลข คงเหลือ / จองแล้ว / ส่งมอบแล้ว (แยกจากคำขอที่ยังรอ)
- [ ] รายการคำขอ: ชื่อผู้ขอ, จำนวน, ข้อความ, วันที่, Badge สถานะ
- [ ] ปุ่มตามสถานะ: pending → อนุมัติ/ปฏิเสธ, approved → ยืนยันส่งมอบแล้ว/ยกเลิกนัด, สถานะอื่นไม่มีปุ่ม
- [ ] ทุกการกระทำมี Confirm Dialog
- [ ] จัดการ Error: สต็อกไม่พอ (อัปเดตตัวเลขล่าสุด), คำขอถูกจัดการไปแล้ว (แสดงสถานะล่าสุด)
- [ ] สถานะประกาศเปลี่ยนตามกฎ: คงเหลือ 0 → จองเต็มแล้ว, ส่งมอบครบจำนวนจริง → ส่งมอบครบ, ส่งมอบยังไม่ครบ → คงสถานะเดิม
- [ ] ประกาศหมดอายุ: คำขอ pending หายไป ส่วน approved ยังกดส่งมอบได้
- [ ] ผู้ที่ไม่ใช่เจ้าของเข้า URL นี้ตรง ๆ ต้องได้ 403

**Definition of Done:** ลงประกาศ → มีคนขอ → อนุมัติ → ส่งมอบ → ประกาศปิดครบ โดยตัวเลขคงเหลือไม่ติดลบและไม่เกินจำนวนที่มี

## Phase 8 — Admin: โครงหลังบ้านและจัดการประกาศ

**เป้าหมาย:** แยกหลังบ้านออกจากหน้าบ้านอย่างชัดเจน (Strict Back-office)

**โครงหลังบ้านและ `/admin`**

- [ ] Sidebar: ภาพรวม, ประกาศ, รายงาน, สมาชิก, หมวดหมู่ และตัวเลขรายงานที่รอจัดการ
- [ ] ผู้ใช้ทั่วไปและ Guest เข้า `/admin/*` ไม่ได้ (403 หรือพาไปเข้าสู่ระบบ)
- [ ] หน้าภาพรวม: การ์ดสถิติ (ผู้ใช้, ประกาศที่เปิดอยู่, รายงานรอจัดการ, บัญชีที่ถูกระงับ) และรายการรายงานล่าสุด (การ์ดที่ยังไม่มี endpoint ให้ซ่อนไว้ ไม่แสดงเลข 0)

**หน้า `/admin/listings`**

- [ ] ตาราง: รูปเล็ก, ชื่อ, เจ้าของ, หมวดหมู่, Badge สถานะ, คงเหลือ/ทั้งหมด, จำนวนคำขอ, วันที่ลง
- [ ] ค้นหา กรองสถานะ/หมวดหมู่/สมาชิก และ Pagination
- [ ] ดูรายละเอียดผ่าน Drawer หรือเปิดหน้าสาธารณะ
- [ ] ปุ่มยกเลิกประกาศ พร้อม Confirm Dialog อธิบายผลต่อเนื่อง (คำขอค้างถูกยกเลิก, ของที่จองไว้คืนสต็อก, กู้คืนไม่ได้)
- [ ] ไม่มีปุ่มแก้ไขประกาศ และไม่มีปุ่มลงประกาศ
- [ ] หลังยกเลิก สถานะในตารางอัปเดตและปุ่มถูกปิด (กดซ้ำไม่ได้)
- [ ] หน้าสาธารณะของประกาศแสดงปุ่ม ยกเลิกประกาศนี้ (Admin) และใช้ผลลัพธ์เดียวกับในตาราง

**Definition of Done:** Admin ยกเลิกประกาศที่มีคำขอ pending และ approved ได้ และผู้ขอเห็นสถานะที่อัปเดตในหน้า /reservations/my

## Phase 9 — Admin: รายงาน, สมาชิก, หมวดหมู่

**หน้า `/admin/reports`**

- [ ] ตาราง: ประกาศที่ถูกรายงาน, ผู้รายงาน, เหตุผล (ชิปสี), วันที่, Badge สถานะ
- [ ] กรองตามสถานะและเหตุผล
- [ ] Drawer รายละเอียด: ข้อความของผู้รายงาน, พรีวิวประกาศ, ประวัติสถานะ
- [ ] ปุ่ม: กำลังตรวจสอบ, ยกเลิกประกาศ, ปิดตั๋ว (resolved), ปฏิเสธรายงาน (rejected)
- [ ] หลังกดยกเลิกประกาศ มีตัวเลือกปิดตั๋วเป็น resolved ต่อทันที
- [ ] ปฏิเสธรายงานแล้วต้องไม่แตะต้องประกาศของสมาชิก
- [ ] ปุ่มลัด ระงับบัญชีเจ้าของ

**หน้า `/admin/users`**

- [ ] ตาราง: ชื่อ, อีเมล, วันที่สมัคร, สถานะ (ใช้งาน/ถูกระงับ), จำนวนประกาศ
- [ ] ค้นหาชื่อหรืออีเมล และกรองสถานะ
- [ ] ระงับบัญชี: Modal ยืนยัน บังคับกรอกเหตุผล และแจ้งว่าจะตัด Session ทันที (ทำช่องเหตุผลไว้ก่อน และส่งไปกับคำสั่งระงับเมื่อ API รองรับการเก็บ)
- [ ] ปลดระงับบัญชี (ปุ่มเขียว)
- [ ] ไม่มีตัวเลือกเปลี่ยน role หรือแต่งตั้ง Admin ใน UI ทุกจุด และฝั่งเซิร์ฟเวอร์ไม่ประมวลผลฟิลด์ role ที่ส่งมากับคำสั่งระงับ/ปลดระงับ
- [ ] ทดสอบ: ผู้ใช้ที่ถูกระงับกดทำรายการต่อทันที ต้องเห็นข้อความ บัญชีของคุณถูกระงับการใช้งาน
