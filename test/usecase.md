## 1. ภาพรวมและแนวทางการทดสอบ (Overview & Test Setup)

เอกสารฉบับนี้รวบรวมกรณีทดสอบ (Use Cases) สำหรับตรวจสอบการทำงานของระบบเว็บแอปพลิเคชันและ API ทั้งในกรณีการทำงานปกติ (Happy Path), กรณีเกิดข้อผิดพลาด (Edge Cases & Validation), และกรณีการละเมิดสิทธิ์ความปลอดภัย (Security & Business Rule Enforcement) เพื่อใช้ตรวจสอบงานก่อนส่งมอบและเตรียมความพร้อมสำหรับการนำเสนอ (Demo Program)

| รหัสบัญชี | บทบาท (Role) | อีเมล / รหัสผ่านจำลอง | วัตถุประสงค์ในการทดสอบ |
|:---:|---|---|---|

## 2. หมวดที่ 1: กรณีทดสอบฝั่งผู้เข้าชมทั่วไป (Guest & Public Scenarios)

### UC-PUB-01: การค้นหาและกรองสิ่งของแบบเปิดกว้าง (Open Discovery & Fallback)
- **เงื่อนไขเริ่มต้น:** มีสิ่งของสถานะ `available` อยู่ในระบบอย่างน้อย 3 หมวดหมู่
- **วัตถุประสงค์:** ตรวจสอบการค้นหาด้วย GPS รัศมี และการสลับไปโหมดเลือกพื้นที่ด้วยตนเองเมื่อผู้ใช้ไม่เปิด GPS (FR-01, FR-06)
- **ขั้นตอนการทดสอบ:**
  1. เข้าหน้า `/listings` ในฐานะ Guest
  2. พิมพ์คำค้นหาในช่องค้นหา เช่น *"เสื้อ"* $\rightarrow$ ตรวจสอบว่าระบบค้นหาเฉพาะประกาศที่มีคำว่าเสื้อ
  3. กรองตามหมวดหมู่ *"เสื้อผ้า"* และเลือกสภาพ *"ดี"*
  4. ทดสอบโหมดพื้นที่:
     - **กรณีอนุญาต GPS:** เลือกรัศมี 5 กิโลเมตร $\rightarrow$ ตรวจสอบว่าแสดงผลสิ่งของที่อยู่ในระยะ
     - **กรณีปฏิเสธ GPS:** เลือกระบบระบุพื้นที่ด้วยตนเอง (จังหวัด: *ขอนแก่น*, อำเภอ: *เมือง*, ตำบล: *ในเมือง*)
- **ผลลัพธ์ที่คาดหวัง:**
  - แสดงการ์ดสิ่งของที่ตรงตามเงื่อนไข พร้อมระบุจำนวนที่พบ
  - มีชิปตัวกรองแสดงให้กดลบทีละตัวได้ และมีปุ่มล้างตัวกรองทั้งหมด
  - Query String บน URL อัปเดตตรงตามตัวกรอง (เช่น `?category=clothing&condition=good&province=ขอนแก่น`) สามารถกด Refresh หรือ Copy ลิงก์แล้วได้ผลลัพธ์เดิม

---

### UC-PUB-02: การคุ้มครองข้อมูลส่วนบุคคลในหน้ารายละเอียด (Privacy by Design Masking)
- **เงื่อนไขเริ่มต้น:** มีประกาศของ User A ในระบบ โดยในข้อมูลจริงมีที่อยู่ละเอียด พิกัด GPS และเบอร์โทรศัพท์
- **วัตถุประสงค์:** ตรวจสอบว่าบุคคลทั่วไปต้องไม่เห็นข้อมูลติดต่อและพิกัดที่แม่นยำ (FR-04, FR-13)
- **ขั้นตอนการทดสอบ:**
  1. ในฐานะ Guest เปิดดูหน้ารายละเอียดสิ่งของ `/listings/:id` หรือยิง `GET /api/v1/listings/:id`
  2. สังเกตข้อมูลการนัดรับบนหน้าเว็บ และตรวจสอบ Source Code (Inspect / View Source / Network Response)
- **ผลลัพธ์ที่คาดหวัง:**
  - บน UI แสดงกล่องข้อมูลนัดรับแบบมีแม่กุญแจล็อก 🔒 พร้อมข้อความแจ้งว่าจะเปิดเผยข้อมูลเมื่อได้รับการอนุมัติคำขอแล้วเท่านั้น
  - แสดงเฉพาะพื้นที่ระดับตำบล/อำเภอ/จังหวัด เช่น *"ต.ในเมือง อ.เมือง จ.ขอนแก่น"*
  - ใน JSON Response ฟิลด์ `pickup.address`, `pickup.location.coordinates`, และ `owner.phone` ต้องถูก Masking เป็นค่าว่างหรือไม่ถูกส่งออกมาอย่างเด็ดขาด

---

### UC-PUB-03: การนำทางเข้าสู่ระบบอย่างลื่นไหลเมื่อต้องการทำรายการ (Frictionless Auth & ReturnTo)
- **เงื่อนไขเริ่มต้น:** Guest เปิดหน้ารายละเอียดสิ่งของชิ้นหนึ่งอยู่ เช่น `/listings/item-123`
- **วัตถุประสงค์:** ตรวจสอบการส่งต่อ URL และการรักษาสถานะความต้องการของผู้ใช้ (FR-03, FR-05)
- **ขั้นตอนการทดสอบ:**
  1. ในฐานะ Guest กดปุ่ม *"ขอรับของชิ้นนี้"*
  2. ตรวจสอบการเปลี่ยนหน้าของเบราว์เซอร์
- **ผลลัพธ์ที่คาดหวัง:**
  - ระบบนำทางไปยังหน้า `/auth?returnTo=%2Flistings%2Fitem-123`
  - มีแถบข้อความสีเขียวแจ้งเตือน: *"เข้าสู่ระบบเพื่อขอรับของชิ้นนี้ต่อ"*
  - ป้องกัน Open Redirect: หากส่ง `returnTo=https://evil.com` หรือ `//evil.com` ระบบต้องปฏิเสธและ Redirect ไปหน้าแรก `/` แทน

---

### UC-PUB-04: การสมัครสมาชิกใหม่และการเข้าสู่ระบบอัตโนมัติ (Unified Auth & Auto-Login)
- **เงื่อนไขเริ่มต้น:** อยู่ที่หน้า `/auth?returnTo=%2Flistings%2Fitem-123`
- **วัตถุประสงค์:** ตรวจสอบการสมัครสมาชิกและเข้าสู่ระบบในขั้นตอนเดียว (FR-04)
- **ขั้นตอนการทดสอบ:**
  1. สลับไปแท็บ *"สมัครสมาชิก"*
  2. กรอกข้อมูล:
     - ชื่อ: *สมชาย ใจดี*
     - อีเมล: *somchai@test.com*
     - รหัสผ่าน: *Pass1234!* (ขั้นต่ำ 8 ตัว)
     - เบอร์โทร: *0812345678*
  3. กดยืนยันการสมัครสมาชิก
- **ผลลัพธ์ที่คาดหวัง:**
  - ได้รับ HTTP `201 Created` และเซิร์ฟเวอร์ออก Session Cookie ให้อัตโนมัติ (ไม่ต้องกรอกรหัสผ่านเพื่อล็อกอินซ้ำ)
  - หน้าเว็บพากลับมายัง `/listings/item-123` ทันที และ Header ปรับเปลี่ยนเป็นมุมมองสมาชิก (Member) มีปุ่มโปรไฟล์ขึ้นมาอย่างถูกต้อง

## 3. หมวดที่ 2: กรณีทดสอบฝั่งผู้ขอรับสิ่งของ (Requester Scenarios)

### UC-REQ-01: การส่งคำขอรับของตามปกติ (Happy Path Reservation)
- **เงื่อนไขเริ่มต้น:** User B ล็อกอินอยู่ และเปิดดูประกาศของ User A ที่มีของคงเหลือ (`availableQuantity` = 2)
- **วัตถุประสงค์:** ตรวจสอบการส่งคำขอรับสิ่งของ (FR-10)
- **ขั้นตอนการทดสอบ:**
  1. User B กดปุ่ม *"ขอรับของชิ้นนี้"*
  2. ใน Modal ระบุจำนวนที่ขอรับ: `1` ชิ้น
  3. กรอกข้อความ: *"สะดวกไปรับช่วงบ่าย 3 โมงครับ"*
  4. กดยืนยันส่งคำขอ (`POST /api/v1/listings/:id/reservations`)
- **ผลลัพธ์ที่คาดหวัง:**
  - ได้รับ HTTP `201 Created`
  - หน้าต่าง Modal ปิดลง และมี Toast สีเขียวแจ้งเตือน *"ส่งคำขอรับของสำเร็จ"*
  - ปุ่มบนหน้าประกาศเปลี่ยนสถานะเป็นปิดใช้งาน (Disabled) พร้อมข้อความ: *"คุณเคยส่งคำขอสำหรับสิ่งของชิ้นนี้ไปแล้ว"* พร้อมลิงก์ไปหน้า `/reservations/my`
  - ยอดคงเหลือของประกาศยังไม่ถูกตัด (ยังคงเหลือ 2 ชิ้น) เนื่องจากอยู่ในสถานะรอพิจารณา (`pending`)

---

### UC-REQ-02: กฎเหล็กห้ามขอซ้ำตลอดชีพ (Single Lifetime Reservation Enforcement)
- **เงื่อนไขเริ่มต้น:** User B เคยส่งคำขอในประกาศนี้ไปแล้ว (ไม่ว่าสถานะคำขอปัจจุบันจะเป็น `pending`, `rejected`, หรือ `cancelled`)
- **วัตถุประสงค์:** ป้องกันการกดสแปมและรับประกันข้อตกลง Single Lifetime Reservation (FR-10)
- **ขั้นตอนการทดสอบ:**
  1. User B พยายามยิงคำขอซ้ำในประกาศเดิมผ่าน Postman/Fetch:
     ```http
     POST /api/v1/listings/:id/reservations
     Content-Type: application/json
     { "quantity": 1, "message": "ขอใหม่อีกรอบครับ" }
     ```
- **ผลลัพธ์ที่คาดหวัง:**
  - เซิร์ฟเวอร์ตอบกลับ `HTTP 409 Conflict`
  - ข้อความแจ้งเตือน: *"คุณเคยส่งคำขอรับสิ่งของในประกาศนี้แล้ว ไม่สามารถส่งคำขอซ้ำได้"*
  - ฐานข้อมูลไม่สร้างเอกสาร Reservation ใหม่ (คงสถานะคำขอเดิมไว้)

---

### UC-REQ-03: การพยายามขอรับสิ่งของของตนเอง (Self-Request Prevention)
- **เงื่อนไขเริ่มต้น:** User A เข้าสู่ระบบ และเปิดดูประกาศที่ตนเองเป็นเจ้าของ
- **วัตถุประสงค์:** ป้องกันไม่ให้เจ้าของส่งคำขอรับของของตนเอง
- **ขั้นตอนการทดสอบ:**
  1. User A พยายามส่งคำขอรับของในประกาศของตนเอง:
     ```http
     POST /api/v1/listings/:myListingId/reservations
     ```
- **ผลลัพธ์ที่คาดหวัง:**
  - บน UI: ซ่อนปุ่มขอรับของ และแสดงปุ่ม *"จัดการคำขอ"* แทน
  - ในระดับ API: เซิร์ฟเวอร์ตอบกลับ `HTTP 400 Bad Request` พร้อมข้อความ *"ไม่สามารถส่งคำขอรับสิ่งของของตนเองได้"*

---

### UC-REQ-04: การยกเลิกคำขอรับของตนเอง (Requester Cancel Request)
- **เงื่อนไขเริ่มต้น:** User B มีคำขอสถานะ `pending` ในประกาศหนึ่ง
- **วัตถุประสงค์:** ผู้ขอสามารถยกเลิกคำขอของตนเองได้เมื่อเปลี่ยนใจ (FR-12)
- **ขั้นตอนการทดสอบ:**
  1. User B เข้าหน้า `/reservations/my`
  2. กดปุ่ม *"ยกเลิกคำขอ"* ในการ์ดคำขอดังกล่าว
  3. ยืนยันใน Confirm Dialog
- **ผลลัพธ์ที่คาดหวัง:**
  - ส่งคำขอ `PATCH /api/v1/reservations/:id/cancel` สำเร็จ ได้รับ `HTTP 200 OK`
  - สถานะคำขอเปลี่ยนเป็น `cancelled`
  - ข้อความในการ์ดระบุ: *"คุณยกเลิกคำขอนี้แล้ว"* และปุ่มกดยกเลิกหายไป

---

### UC-REQ-05: การได้รับการอนุมัติและเปิดเผยข้อมูลนัดรับ (Approved Contact Revelation)
- **เงื่อนไขเริ่มต้น:** User A (เจ้าของ) กดอนุมัติคำขอของ User B เรียบร้อยแล้ว
- **วัตถุประสงค์:** ตรวจสอบการแจ้งเตือน Notification Badge และการเปิดเผยสถานที่ติดต่อ (FR-13, FR-11)
- **ขั้นตอนการทดสอบ:**
  1. User B สังเกตแถบนำทาง (Header) ด้านบน
  2. User B เปิดดูหน้ารายละเอียดของคำขอใน `/reservations/my` หรือ `/listings/:id`
- **ผลลัพธ์ที่คาดหวัง:**
  - บน Header ของ User B ปรากฏตัวนับ Badge สีแดง (`unreadCount` = 1) ที่เมนูคำขอของฉัน
  - การ์ดคำขอเปลี่ยนสถานะเป็น `approved` (สีเขียว)
  - กล่องข้อมูลนัดรับปลดล็อก 🔓: แสดงที่อยู่ละเอียดจริง เช่น *"อาคาร SC-06 ชั้น 1 ฝั่งห้องสมุด"*, แสดงเบอร์โทรศัพท์ของ User A, และแสดงช่วงเวลาที่นัดรับได้ พร้อมปุ่มคัดลอกเบอร์โทร

---

### UC-REQ-06: การเคลียร์ Notification Badge เมื่อเปิดดูหน้าคำขอ
- **เงื่อนไขเริ่มต้น:** User B มี Badge แจ้งเตือนสีแดงค้างอยู่ที่ Header (`unreadCount` > 0)
- **วัตถุประสงค์:** เคลียร์การแจ้งเตือนเมื่อผู้ใช้รับทราบแล้ว (FR-11)
- **ขั้นตอนการทดสอบ:**
  1. User B คลิกเข้ามาที่หน้า `/reservations/my`
  2. สังเกตตัวนับ Badge บน Header
- **ผลลัพธ์ที่คาดหวัง:**
  - หน้าเว็บส่งคำสั่ง `PATCH /api/v1/reservations/read-all` ไปยังเซิร์ฟเวอร์
  - จุดสีแดงหรือตัวเลขนับแจ้งเตือนบน Navbar หายไปทันที
  - เมื่อรีเฟรชหน้าเว็บ ตัวเลข Badge ยังคงเป็น 0 จนกว่าจะมีคำขอใหม่ได้รับการอัปเดต

## 4. หมวดที่ 3: กรณีทดสอบฝั่งเจ้าของประกาศ (Listing Owner Scenarios)

### UC-OWN-01: การลงประกาศสิ่งของใหม่ (Pickup Only & Validation)
- **เงื่อนไขเริ่มต้น:** User A เข้าสู่ระบบ และเข้าหน้า `/listings/new`
- **วัตถุประสงค์:** ตรวจสอบ Validation และกฎนัดรับด้วยตนเองเท่านั้น (FR-07, Non-functional)
- **ขั้นตอนการทดสอบ:**
  1. กรอกชื่อสิ่งของ: *"พัดลมตั้งโต๊ะ Hatari 16 นิ้ว"*
  2. เลือกหมวดหมู่: *"เครื่องใช้ไฟฟ้า"*
  3. ระบุสภาพ: *"ดี"*
  4. ระบุจำนวน: `1` ชิ้น
  5. กรอกรายละเอียด: *"ใช้งานได้ปกติ ลมแรง มีฝุ่นเกาะเล็กน้อย"*
  6. ใส่รูปภาพ URL: `https://example.com/fan.jpg` (1 รูป)
  7. ส่วนการนัดรับ: ตรวจสอบตัวเลือกการจัดส่ง $\rightarrow$ ต้องมีเฉพาะ *"นัดรับด้วยตนเองเท่านั้น (Pickup Only)"*
  8. ระบุที่อยู่นัดรับละเอียด: *"หอพักนักศึกษาชาย อาคาร 2"* และเลือกพื้นที่ *"ขอนแก่น / เมือง / ในเมือง"*
  9. กำหนดวันหมดอายุ: วันที่ในอนาคต (อีก 7 วัน)
  10. กดยืนยันสร้างประกาศ
- **ผลลัพธ์ที่คาดหวัง:**
  - ได้รับ `HTTP 201 Created`
  - นำทางไปยังหน้ารายละเอียดประกาศที่เพิ่งสร้าง `/listings/:newId`
  - ข้อมูลที่อยู่ละเอียดถูกซ่อนไว้สำหรับคนอื่น และเปิดให้เห็นเฉพาะเจ้าของประกาศ

### UC-OWN-02: การแก้ไขประกาศก่อนมีคำขอ (Pre-Reservation Edit)
- **เงื่อนไขเริ่มต้น:** ประกาศที่เพิ่งสร้างขึ้นมา ยังไม่มีใครส่งคำขอรับของเข้ามาเลย (`Reservation.exists` เป็น false)
- **วัตถุประสงค์:** เจ้าของสามารถแก้ไขข้อมูลประกาศได้ตราบใดที่ยังไม่มีคำขอแรก (FR-08)
- **ขั้นตอนการทดสอบ:**
  1. User A กดปุ่ม *"แก้ไขประกาศ"* (`/listings/:id/edit`)
  2. เปลี่ยนแปลงหัวข้อเป็น: *"พัดลมตั้งโต๊ะ Hatari 16 นิ้ว (พร้อมสายชาร์จ)"*
  3. เปลี่ยนแปลงจำนวนเป็น: `2` ชิ้น
  4. กดยืนยันการแก้ไข
- **ผลลัพธ์ที่คาดหวัง:**
  - ส่ง `PATCH /api/v1/listings/:id` สำเร็จ ได้รับ `HTTP 200 OK`
  - ข้อมูลในประกาศอัปเดตตามที่แก้ไขเรียบร้อย

---

### UC-OWN-03: กฎเหล็กล็อกการแก้ไขเมื่อมีคำขอแรก (Strict Edit Lock)
- **เงื่อนไขเริ่มต้น:** ประกาศของ User A มีคำขอของ User B เข้ามาแล้ว 1 คำขอ (ไม่ว่าคำขอจะสถานะ `pending`, `approved`, หรือ `rejected`)
- **วัตถุประสงค์:** ห้ามแก้ไขประกาศโดยเด็ดขาดเพื่อป้องกันข้อพิพาทและบิดเบือนข้อตกลง (FR-08)
- **ขั้นตอนการทดสอบ:**
  1. User A พยายามเข้าหน้า `/listings/:id/edit` หรือส่งคำสั่ง `PATCH /api/v1/listings/:id`
- **ผลลัพธ์ที่คาดหวัง:**
  - บน UI: ปุ่มแก้ไขในหน้าจัดการประกาศถูกปิดเป็นสีเทา (Disabled) พร้อม Tooltip แจ้ง: *"ไม่สามารถแก้ไขได้เนื่องจากมีคำขอรับของเกิดขึ้นแล้ว"*
  - ในหน้าแก้ไข: ปิดทุกช่องฟอร์ม เหลือเฉพาะปุ่ม *"ยกเลิกประกาศ"*
  - ในระดับ API: เซิร์ฟเวอร์ตอบกลับ `HTTP 409 Conflict` พร้อมข้อความ: *"ไม่สามารถแก้ไขประกาศได้เนื่องจากมีคำขอเกิดขึ้นในประกาศนี้แล้ว"*

---

### UC-OWN-04: การอนุมัติคำขอแบบ Atomic (Atomic Stock Reservation)
- **เงื่อนไขเริ่มต้น:** ประกาศมี `quantity` = 1, `availableQuantity` = 1 และมีคำขอของ User B รออยู่ (`quantity` = 1, `status` = "pending")
- **วัตถุประสงค์:** ตัดสต็อกอย่างถูกต้องและปรับสถานะประกาศเป็น reserved อัตโนมัติ (FR-11)
- **ขั้นตอนการทดสอบ:**
  1. User A เข้าหน้าจัดการคำขอ `/listings/:id/reservations`
  2. กดปุ่ม *"อนุมัติ"* คำขอของ User B
- **ผลลัพธ์ที่คาดหวัง:**
  - เซิร์ฟเวอร์รัน Atomic Operation (`availableQuantity: { $gte: 1 }`, `$inc: { availableQuantity: -1 }`)
  - ได้รับ `HTTP 200 OK`
  - สถานะคำขอของ User B เปลี่ยนเป็น `approved`
  - ประกาศมี `availableQuantity` เหลือ `0` และสถานะประกาศเปลี่ยนเป็น `"reserved"` (จองเต็มแล้ว) โดยอัตโนมัติ

---

### UC-OWN-05: การปฏิเสธคำขอและคืนสต็อก (Reject & Stock Release)
- **เงื่อนไขเริ่มต้น:** ประกาศมีคำขอของ User B ที่เคยได้รับการอนุมัติ (`approved`) ไว้ และประกาศอยู่ในสถานะ `reserved`
- **วัตถุประสงค์:** เมื่อเจ้าของปฏิเสธคำขอที่เคยอนุมัติ ต้องคืนสต็อกและปลดสถานะประกาศกลับมาเปิดรับใหม่ (FR-12)
- **ขั้นตอนการทดสอบ:**
  1. User A กดปุ่ม *"ปฏิเสธคำขอ"* ของ User B
- **ผลลัพธ์ที่คาดหวัง:**
  - คำขอของ User B เปลี่ยนสถานะเป็น `rejected`
  - สต็อกคงเหลือของประกาศคืนกลับมา 1 ชิ้น (`availableQuantity` = 1)
  - สถานะประกาศปลดจาก `reserved` กลับมาเป็น `"available"` (พร้อมรับ) ทันที เพื่อให้ผู้อื่นสามารถขอรับต่อได้

---

### UC-OWN-06: การยืนยันส่งมอบสำเร็จจบงานฝ่ายเดียว (One-Party Completion)
- **เงื่อนไขเริ่มต้น:** ประกาศมีของทั้งหมด `quantity` = 1 ชิ้น และคำขอของ User B อยู่ในสถานะ `approved`
- **วัตถุประสงค์:** เจ้าของเป็นผู้กดยืนยันส่งมอบฝ่ายเดียวเพื่อปิดงาน (FR-14, One-Party Completion)
- **ขั้นตอนการทดสอบ:**
  1. เมื่อมีการส่งมอบของจริงแล้ว User A กดปุ่ม *"ยืนยันส่งมอบแล้ว"* (`PATCH /api/v1/reservations/:id/complete`)
- **ผลลัพธ์ที่คาดหวัง:**
  - คำขอของ User B เปลี่ยนสถานะเป็น `completed` พร้อมบันทึกเวลา `completedAt`
  - เนื่องจากยอดส่งมอบครบตามยอดประกาศทั้งหมด (1/1 ชิ้น) สถานะประกาศจึงเปลี่ยนเป็น `"completed"` (ส่งมอบครบแล้ว) ปิดรอบการแบ่งปันอย่างสมบูรณ์

---

### UC-OWN-07: กฎเหล็กการยกเลิกแบบต่อเนื่อง (Cascade Cancellation)
- **เงื่อนไขเริ่มต้น:** ประกาศมี `quantity` = 3 ชิ้น โดยมีคำขอของ User B (`pending`), คำขอของ User C (`approved`), และคำขอของ User D (`completed` จากรอบก่อน)
- **วัตถุประสงค์:** เมื่อประกาศถูกยกเลิก คำขอที่ค้างอยู่ทั้งหมดต้องถูกยกเลิกเป็น cancelled พร้อมกันทันที (FR-09, Cascade Cancellation)
- **ขั้นตอนการทดสอบ:**
  1. User A กดปุ่ม *"ยกเลิกประกาศ"* ในหน้า `/users/me/listings`
  2. ยืนยันใน Confirm Dialog
- **ผลลัพธ์ที่คาดหวัง:**
  - ประกาศเปลี่ยนสถานะเป็น `"cancelled"`
  - **คำขอของ User B (เดิม `pending`):** เปลี่ยนเป็น `"cancelled"` พร้อมตั้ง `isRead: false`
  - **คำขอของ User C (เดิม `approved`):** เปลี่ยนเป็น `"cancelled"` คืนสต็อก และตั้ง `isRead: false`
  - **คำขอของ User D (เดิม `completed`):** คงสถานะเดิมเป็น `completed` ห้ามเปลี่ยนแปลงเพื่อความถูกต้องของประวัติ
  - เมื่อ User B และ User C เข้าหน้า `/reservations/my` จะเห็นสถานะคำขอเป็น *"ยกเลิกแล้ว"* พร้อมข้อความอธิบาย: *"ประกาศนี้ถูกยกเลิกโดยเจ้าของ"*

---

## 5. หมวดที่ 4: กรณีทดสอบฝั่งผู้ดูแลระบบ (Admin Scenarios)

### UC-ADM-01: การตรวจสอบสิทธิ์การเข้าถึงหลังบ้าน (Back-office Isolation)
- **เงื่อนไขเริ่มต้น:** มีผู้ใช้ทั้ง 3 บทบาท (Guest, Member ธรรมดา, และ Admin)
- **วัตถุประสงค์:** ป้องกันไม่ให้ผู้ใช้ทั่วไปเข้าถึงเส้นทางของผู้ดูแลระบบ (FR-17)
- **ขั้นตอนการทดสอบ:**
  1. **กรณี Guest:** พิมพ์ URL ตรงเข้าไปที่ `/admin` หรือยิง `GET /api/v1/users`
  2. **กรณี Member (User A):** พิมพ์ URL ตรงเข้าไปที่ `/admin` หรือยิง `GET /api/v1/users`
  3. **กรณี Admin:** ล็อกอินด้วยบัญชี Admin แล้วเข้า `/admin`
- **ผลลัพธ์ที่คาดหวัง:**
  - Guest: ได้รับ `HTTP 401 Unauthorized` และหน้าเว็บพาไปที่ `/auth`
  - Member ธรรมดา: ได้รับ `HTTP 403 Forbidden` และหน้าเว็บแสดงหน้าข้อผิดพลาด `403.ejs`
  - Admin: เข้าสู่หน้าแดชบอร์ดหลังบ้านได้ตามปกติ

---

### UC-ADM-02: การดึงสถิติภาพรวมแดชบอร์ด (Admin Dashboard Stats)
- **เงื่อนไขเริ่มต้น:** Admin ล็อกอินอยู่ และเข้าสู่หน้าแรกของ `/admin`
- **วัตถุประสงค์:** ตรวจสอบความถูกต้องของการดึงข้อมูลสถิติภาพรวม (Phase 8, PlanUI2)
- **ขั้นตอนการทดสอบ:**
  1. หน้าบ้านยิง `GET /api/v1/admin/stats`
- **ผลลัพธ์ที่คาดหวัง:**
  - ได้รับ `HTTP 200 OK` พร้อมข้อมูล:
    ```json
    {
      "success": true,
      "data": {
        "totalUsers": 15,
        "suspendedUsers": 1,
        "activeListings": 8,
        "pendingReports": 2
      }
    }
    ```
  - บน UI หน้า `/admin` นำตัวเลขไปแสดงผลบนการ์ดสถิติ 4 ใบได้อย่างถูกต้อง ไม่ขึ้นเลข 0 หรือข้อความสมมติ

---

### UC-ADM-03: แอดมินสั่งระงับประกาศที่มีปัญหา (Admin Cancel Listing + Cascade)
- **เงื่อนไขเริ่มต้น:** มีประกาศที่ผิดกฎชุมชน และมีคำขอ pending ค้างอยู่
- **วัตถุประสงค์:** แอดมินสามารถระงับประกาศได้ และทริกเกอร์ Cascade Cancellation อัตโนมัติ (FR-17)
- **ขั้นตอนการทดสอบ:**
  1. Admin เข้าหน้า `/admin/listings`
  2. กดปุ่ม *"ยกเลิกประกาศ"* ในแถวประกาศที่มีปัญหา ระบุเหตุผล: *"มีเนื้อหาเข้าข่ายสิ่งผิดกฎหมาย"*
  3. ยืนยันการทำรายการ (`PATCH /api/v1/admin/listings/:id/status` ด้วย `{ status: "cancelled", reason: "..." }`)
- **ผลลัพธ์ที่คาดหวัง:**
  - ได้รับ `HTTP 200 OK`
  - ประกาศถูกปรับเป็นสถานะ `cancelled`
  - คำขอที่ค้างอยู่ของผู้ใช้ทั้งหมดถูก Cascade เปลี่ยนเป็น `cancelled` ทันที

---

### UC-ADM-04: การระงับบัญชีสมาชิกและการตัด Session ทันที (Ban & Immediate Session Invalidation)
- **เงื่อนไขเริ่มต้น:** User C กำลังล็อกอินใช้งานอยู่ในเบราว์เซอร์ A และ Admin กำลังใช้งานอยู่ในเบราว์เซอร์ B
- **วัตถุประสงค์:** เมื่อแอดมินสั่งแบน ผู้ใช้ต้องถูกตัดสิทธิ์การใช้งานทันที ไม่สามารถคลิกทำรายการต่อได้ (FR-17, Security Isolation)
- **ขั้นตอนการทดสอบ:**
  1. Admin เข้าหน้า `/admin/users` ค้นหาชื่อ User C
  2. กดปุ่ม *"ระงับบัญชี"* กรอกเหตุผล: *"สแปมข้อความและโพสต์เนื้อหาหลอกลวง"* และกดยืนยัน
  3. ไปที่หน้าต่างเบราว์เซอร์ของ User C ทันที แล้วกดคลิกทำรายการ เช่น กดค้นหาของ หรือกดเข้าโปรไฟล์ตนเอง
- **ผลลัพธ์ที่คาดหวัง:**
  - ในฝั่ง Admin: ได้รับ `HTTP 200 OK` และในฐานข้อมูลบันทึก `isActive: false`, `banReason`, และ `bannedAt` ลงบนโมเดล User
  - เซิร์ฟเวอร์ค้นหาและลบ Session ของ User C ออกจากคอลเลกชัน `sessions` ใน MongoDB ทันที
  - ในฝั่ง User C: เมื่อกดทำรายการ จะได้รับ `HTTP 401 Unauthorized` ทันที และหน้าเว็บแสดงข้อความเตือน: *"บัญชีของคุณถูกระงับการใช้งาน"* พร้อมนำทางออกจากระบบ

---

### UC-ADM-05: กฎเหล็กห้ามแต่งตั้งหรือแก้ไข Role ผ่าน API (No Privilege Escalation)
- **เงื่อนไขเริ่มต้น:** Admin พยายามส่งคำสั่งแก้ไขสถานะผู้ใช้
- **วัตถุประสงค์:** ป้องกันไม่ให้แอดมินแต่งตั้งแอดมินคนใหม่ หรือเปลี่ยนสิทธิ์ผ่านระบบหน้าบ้าน (FR-17, Security)
- **ขั้นตอนการทดสอบ:**
  1. ยิง API ตรงผ่านเครื่องมือทดสอบ:
     ```http
     PATCH /api/v1/users/:targetUserId/status
     Content-Type: application/json
     {
       "isActive": true,
       "role": "admin"
     }
     ```
- **ผลลัพธ์ที่คาดหวัง:**
  - ฟิลด์ `role` ต้องไม่ถูกนำไปประมวลผลหรือบันทึกลงฐานข้อมูลอย่างเด็ดขาด
  - ข้อมูลผู้ใช้ในคอลเลกชัน `users` ยังคงเป็น `role: "user"` เหมือนเดิม
  - สิทธิ์การเป็น Admin ทำได้เฉพาะระดับ Database Administrator เท่านั้น

---

### UC-ADM-06: กฎเหล็กแอดมินไม่มีสิทธิ์แก้เนื้อหาหรืออนุมัติแทนเจ้าของ (Admin Permission Isolation)
- **เงื่อนไขเริ่มต้น:** มีประกาศของ User A และมีคำขอของ User B รอการอนุมัติอยู่
- **วัตถุประสงค์:** แอดมินมีหน้าที่กำกับดูแลเท่านั้น ไม่มีสิทธิ์แก้ไขข้อมูลส่วนบุคคลหรือก้าวก่ายการตัดสินใจของสมาชิก
- **ขั้นตอนการทดสอบ:**
  1. Admin พยายามยิง `PATCH /api/v1/listings/:id` เพื่อแก้ชื่อประกาศของ User A
  2. Admin พยายามยิง `PATCH /api/v1/reservations/:resId/approve` เพื่ออนุมัติคำขอแทน User A
- **ผลลัพธ์ที่คาดหวัง:**
  - การแก้ไขประกาศ: ได้รับ `HTTP 403 Forbidden` เสมอ (เฉพาะเจ้าของประกาศเท่านั้น)
  - การอนุมัติคำขอ: ได้รับ `HTTP 403 Forbidden` เสมอ (เฉพาะเจ้าของประกาศตัวจริงเท่านั้น)

### UC-ADM-07: การตรวจสอบและจัดการรายงานปัญหา (Reports Management)
- **เงื่อนไขเริ่มต้น:** User C ส่งรายงานปัญหาประกาศชิ้นหนึ่งเข้ามาด้วยเหตุผล *"spam"*
- **วัตถุประสงค์:** แอดมินสามารถตรวจดูคิวรายงาน เปลี่ยนสถานะ และตัดสินใจปิดตั๋ว (FR-16, FR-17)
- **ขั้นตอนการทดสอบ:**
  1. Admin เข้าหน้า `/admin/reports`
  2. กรองดูรายงานสถานะ `pending`
  3. คลิกเปิด Drawer ดูรายละเอียดข้อความของผู้รายงานและพรีวิวประกาศ
  4. อัปเดตสถานะตั๋วรายงานเป็น `reviewing` $\rightarrow$ จากนั้นเลือกปิดตั๋วเป็น `resolved`
- **ผลลัพธ์ที่คาดหวัง:**
  - ส่งคำขอ `PATCH /api/v1/reports/:id` สำเร็จ ได้รับ `HTTP 200 OK`
  - ตั๋วรายงานถูกปรับสถานะเป็น `resolved` และหายไปจากคิวงานรอตรวจสอบ

### UC-ADM-08: การตรวจสอบจำนวนประกาศที่ใช้ก่อนลบหมวดหมู่ (Category Usage Check)
- **เงื่อนไขเริ่มต้น:** หมวดหมู่ *"อาหาร"* มีประกาศผูกอยู่ 5 ประกาศ
- **วัตถุประสงค์:** ตรวจสอบ `usageCount` เพื่อป้องกันการลบหมวดหมู่ที่มีการใช้งานอยู่ (PlanUI Phase 9)
- **ขั้นตอนการทดสอบ:**
  1. Admin เข้าหน้า `/admin/categories`
  2. สังเกตคอลัมน์ *"จำนวนประกาศที่ใช้"* ในตารางหมวดหมู่อาหาร
  3. Admin ลองกดปุ่มลบหมวดหมู่อาหาร
- **ผลลัพธ์ที่คาดหวัง:**
  - ตารางแสดงผล `usageCount: 5` ได้อย่างถูกต้อง
  - เมื่อสั่งลบ (`DELETE /api/v1/categories/:id`) เซิร์ฟเวอร์จะไม่ลบ Document ออกจากฐานข้อมูล แต่จะทำ Soft-delete โดยปรับ `isActive: false` เพื่อไม่ให้กระทบต่อประวัติของประกาศเดิม
